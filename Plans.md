## Phase 96: Fix WorktreeCreate hook — remove stdout output (root cause of JSON-named directories)

Created: 2026-05-12

**Goal**: Fix `HandleWorktreeCreate` so it never writes to stdout. `WorktreeCreate` is a lifecycle/notification event — CC does not expect or consume a response from it. The handler was emitting `{"decision":"approve","reason":"WorktreeCreate: initialized worktree state"}` on every invocation. CC was picking up this output and, on some invocations, appending it to the `cwd` field fed into the next WorktreeCreate event, causing `os.MkdirAll` to create a directory literally named `{"decision":"approve",...}` inside the project folder (observed at `/Users/hbai/Documents/pri/playground/ti-status/{...}`).

**Root cause**: `writeWorktreeApprove` was called on every code path (success and all early-exit guards), writing JSON to `os.Stdout`. Decision-response JSON belongs only on permission hooks (`PreToolUse`, `PermissionRequest`), not notification hooks.

**Fix**: Change `HandleWorktreeCreate` signature to accept `_ io.Writer` and remove all stdout writes. Retain the `{}` guard in the CWD validation as defense-in-depth — then removed at PM request since the root cause is gone. Update tests to assert zero stdout output instead of asserting approve-JSON format. Rebuild binary.

## Phase 94: Token savings — simplify harness plugin for plugin users

Created: 2026-05-07

**Goal**: Reduce per-session and per-invocation token costs for plugin users by (a) moving verbose inline content from skill bodies to lazy-loaded `references/` files, (b) consolidating thin internal-only skills, and (c) trimming the worker agent file.

**Source**: `/simplify` analysis (this session). Three review agents (reuse, quality, efficiency) audited the full plugin and ranked findings into Tier 1 (high impact, low effort) and Tier 2 (meaningful, larger scope). Tier 3 findings were false positives (early-exit guards already exist; `PermissionRequest if:` list is intentionally specific).

**Token cost anatomy** (where savings come from):
- **Per-session constant**: 30 skill descriptions in system-reminder (~1,100 tokens/session). Demoting a thin skill to a reference file removes one slot.

- **Per-Worker-dispatch**: `worker.md` is 264 lines; ~50 lines are Codex-CLI edge cases that 90%+ of users never need.

**Non-goals**: No changes to `hooks.json` permission patterns (intentionally specific for security). No changes to `fix-proposal-injector.sh` / `breezing-signal-injector.sh` (already have proper early-exit guards on lines 34 and 25 respectively). No skill renaming that would break user muscle memory beyond the documented merge in 94.4.

## Phase 89: Bring Ralph Loop into Harness — `[ralph]` tasks in `harness-plan` + new `harness-ralph-loop` skill driving subagent iteration

Created: 2026-05-03

**Goal**: Add a Ralph-Wiggum-style iterative-loop execution mode to harness. `harness-plan` learns to detect Ralph-suitable tasks (well-defined success criteria, "iterate-until-pass" patterns) and emits them with a new `[ralph]` marker plus per-task `Verify:` and `MaxIter:` lines. A new `harness-ralph-loop` skill orchestrates the loop: it owns one persistent worktree, dispatches a fresh `harness:ralph-worker` subagent per iteration, runs the verify command authoritatively (anti-tamper hard stop on worker self-report mismatch), scans for both a `<promise>{DoD}</promise>` text tag and a structured `ralph-worker-report.v1` field, diffs the worktree to detect stuck iterations, and stops on success / `FT-RALPH-01` / `FT-RALPH-02` / `FT-RALPH-03`. `harness-work` delegates `[ralph]` tasks to the new skill.

**Motivation**: Many harness tasks already match Ralph's sweet spot (greenfield "build until tests green", fix loops, refactors with regression coverage), but harness has no mechanism to express "iterate until X exits 0". The upstream `/ralph-loop` plugin can't be reused as-is because its Stop hook is session-bound and won't fire inside a Task subagent — and the user wants Ralph work to run in subagents (isolation, parallelism with non-Ralph tasks). So harness builds its own orchestrator that mirrors Ralph's "same prompt, see your work via files" philosophy without depending on the Stop-hook plumbing.

**Source**: User request (this session) + opus-agent architectural review at `/Users/hbai/.claude/plans/help-me-investigate-serialized-curry.md` (full design + decisions table). Opus review corrected three premises: (1) `isolation="worktree"` is fresh-per-call so the orchestrator must drive worktree reuse via `EnterWorktree(path=...)`; (2) the existing `claude-code-harness:worker` agent cannot be reused (hard-coded `isolation: worktree` in frontmatter, TDD-shaped initialPrompt, SR-5 conflicts with Ralph's scratchpad-file pattern) — a sibling `ralph-worker` agent is required; (3) verifier-mismatch (worker self-reports verify pass when actual verify fails) is a load-bearing hard stop, not just a warning.

**Non-goals**: parallel execution of multiple `[ralph]` tasks (deferred — each main session can drive one Ralph orchestrator at a time, sequential by default); upstreaming the orchestrator pattern back to `/ralph-loop` plugin; cross-session resume after `/clear` mid-loop (worktree path is durable but loop state isn't checkpointed yet).

## Phase 86: PII Guard email allowlist for GitHub noreply addresses + rebrand block message to Powerball Harness PII Guard

Created: 2026-05-01

> **Editing convention for this phase**: The PII Guard hooks scan this file and the unfixed `email-address` rule will block any literal email-shape. Whenever this phase needs to refer to an email, ALWAYS wrap the local part in angle brackets — e.g. `<USER>@users.noreply.github.com` or `<ID>+<USER>@users.noreply.github.com`. The angle brackets break the word boundary the regex requires, so the engine never sees a match. Bare email-shape literals (with a real local-part before the `@`) are forbidden until task 86.1 ships. The Phase 85 reserved names continue to apply only when expanded verbatim.

**Goal**: Two small, related polish items reducing PII Guard noise and clarifying ownership of the warning text:
1. **Email allowlist for GitHub noreply addresses**: stop flagging emails whose domain part is `users.noreply.github.com`. These are GitHub's privacy-preserving commit/PR addresses — designed to be public, never personal contact info — so blocking them is pure noise. Both forms must pass: the legacy `<USER>@users.noreply.github.com` and the modern numeric-prefix `<ID>+<USER>@users.noreply.github.com`. A whole-domain match (after the last `@`) covers both.
2. **Rebrand block/warn messages to "Powerball Harness PII Guard"**: the current text says generic "Privacy Guard" / "🛡️ Privacy Guard blocked this submission". Users seeing the warning don't know which system flagged it or that it's a Powerball-specific guardrail (vs. a generic Claude Code feature). Replace all five user-facing strings in `go/cmd/harness/hook_pii.go` with "Powerball Harness PII Guard".

**Motivation**: User reported (a) GitHub noreply commit emails are flagged as PII even though they're explicitly designed for public exposure — the whole point of the noreply domain is to be safe to publish — and (b) the block message reads as a generic "security guard" with no Powerball Harness branding, so users can't tell what system flagged them or where to look for documentation. Both are 30-minute fixes that compose cleanly with the Phase 85 `Validator` field already on the `Rule` struct.

**Source**: New work, requested by user. Builds on the per-rule `Validator` field added in Phase 85 task 85.1 (`go/internal/piiguard/rule.go:44`) and the `formatPromptBlockReason` / `formatPostToolContext` text introduced in Phase 83.

**Risk notes**:
- **Allowlist-by-domain over-trust**: a phisher could spoof a `From:` header claiming the noreply domain in pasted email content. Mitigation: the allowlist only suppresses the *PII tag* on the email itself, not any of the surrounding content. If the surrounding content contains a real secret (token, key, etc.), the other rules still fire. Email-only false-negatives are acceptable for a domain that is by design public.
- **Substring confusion**: a naive suffix match would also pass a decoy like `evil-users.noreply.github.com.attacker.example` — the validator uses `strings.EqualFold` on the full domain (everything after the last `@`), not `strings.HasSuffix`, to prevent this. Test case (d) in task 86.1 asserts this explicitly.
- **Rebrand string-coupling**: any external doc, README, or screenshot asserting on the old "Privacy Guard" wording will drift. Mitigation: search the repo for "Privacy Guard" before merging — `grep -rn 'Privacy Guard' .` — and either update or note the drift in the CHANGELOG. Most matches will be in `piiguard` upstream-provenance comments which intentionally stay.
- **Fixture-write self-block**: same bootstrap problem as Phase 85 task 85.4 — writing the negative fixture via Edit/Write triggers the unfixed PII Guard hook. The task DoD pre-emptively mentions the workaround. Building task 86.1 first solves it cleanly because the validator then exempts the fixture content.
- **Future allowlist growth**: if more domains accumulate, the hardcoded slice becomes a churn point. Mitigation: explicitly out-of-scope this phase; revisit as an env-var or settings-file-driven list once the slice exceeds three entries.
- **Editing-convention compliance for this phase block**: any future edit to this Phase 86 block that introduces a literal email shape (without angle-bracket placeholders) will fail the pre-tool-use PII Guard hook until 86.1 ships. After this phase ships, the editing convention can be relaxed in a follow-up edit because noreply-domain literals will pass cleanly.
