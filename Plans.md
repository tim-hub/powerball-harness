## Phase 93: Port upstream v4.4.0→v4.7.0 — configurable R12 protected-branch policy + weak-supervision elicitation pipeline

Created: 2026-05-06

**Goal**: Port two substantive upstream features from `Chachamaru127/claude-code-harness` v4.4.0→v4.7.0 that have clear value to our fork: (a) make R12 protected-branch push policy configurable (ask/deny/allow) instead of hardcoded "warn"; (b) add a weak-supervision elicitation ledger that records `Elicitation` / `ElicitationResult` events as JSONL for downstream advisor / review use.

**Source**: Upstream diff `https://github.com/Chachamaru127/claude-code-harness/compare/v4.4.0...v4.7.0`. Verified missing in local via working-tree symbol greps per `port-upstream` skill rules.

**Skipped (not relevant to our fork)**:
- `go/internal/harnessmem/companion.go` — depends on upstream-specific `@chachamaru127/harness-mem` npm package; our memory system is `harness-remember`, not the same shape
- `opencode/` skills — different AI tool ecosystem
- `skills/harness-loop/SKILL.md` updates — we renamed to `harness-schedule-run` with different content; upstream changes don't apply 1:1
- `hooks.json` duplicate `inject-policy` removal — our hooks.json uses `${CLAUDE_PLUGIN_ROOT}/bin/harness` directly, not the upstream's bash wrapper, so the duplicate doesn't exist
- Japanese-only doc additions where the underlying feature is also non-applicable

**Design notes**:
- For R12: env precedence is `HARNESS_PROTECTED_BRANCH_PUSH_POLICY` → `HARNESS_DIRECT_PUSH_POLICY` → `.claude-code-harness.config.yaml` `safety.protected_branch_push` → `harness.toml` → default `ask`. Upstream values normalize: `ask`/`confirm`→`ask`, `deny`/`block`→`deny`, `allow`/`approve`→`allow`. Default is `ask` (currently we hardcode `warn`, which is closest to `ask` semantically; this is a behavioral change worth flagging in CHANGELOG).
- For elicitation ledger: drop the upstream `HarnessMemClient` DI field and the `client.postElicitationEvent(...)` call entirely — our fork has no harness-mem bridge. Keep only the `appendElicitationEvent(projectRoot, event)` JSONL write to `.claude/state/elicitation/events.jsonl`. Schema version `elicitation-event.v1`. Allowed event kinds: `capability_probe`, `weak_label`, `judge_verdict`, `eval_result`, `counterexample`, plus the two implicit ones the handlers emit: request + result.
- Weak-supervision scripts read the ledger written by the Go handlers — port them as-is with our path conventions.

## Phase 92: New `harness-compact` skill — strategic-compaction suggester (inspired by everything-claude-code)

Created: 2026-05-06

**Goal**: Add a new `harness-compact` skill that proactively suggests `/compact` at strategic checkpoints (after N tool calls + periodic reminders), so users can preserve context through phase transitions instead of letting auto-compaction fire mid-task. Adapted to harness conventions: per-session counter under `.claude/state/` (not `/tmp/`), wired into `PostToolUse(Edit|Write)` to avoid bloating the already-busy `PreToolUse` chain, and role-aware so it does not nag during `cc:WIP` Worker sessions or `[ralph]` loops.

**Source**: User request (this session). Inspired by `affaan-m/everything-claude-code` — specifically `skills/strategic-compact/SKILL.md` and `skills/strategic-compact/suggest-compact.sh`. Upstream uses `PreToolUse(Edit|Write)`, a `/tmp` counter file, and stderr-only output at thresholds 50 / 25; this port adapts each of those to harness state and hook conventions.

**Non-goals**: Modifying the existing PreCompact handoff-artifact pipeline (`scripts/hook-handlers/pre-compact-save.js`) or the PostCompact re-injection (`scripts/hook-handlers/post-compact.sh`) — those preserve state across compaction and are orthogonal to suggesting *when* to compact. No automatic invocation of `/compact` (suggestion only). No changes to the existing PreCompact role-gate that already blocks Worker compaction with WIP tasks.

**Design notes (assumptions to confirm before /harness-work)**:
- Threshold defaults: 50 tool calls (initial), then every 25 thereafter — match upstream; overridable via `HARNESS_COMPACT_THRESHOLD` / `HARNESS_COMPACT_INTERVAL`
- Counter file: `.claude/state/compact-counter-${CLAUDE_SESSION_ID}.json` — per-session, cleaned by the existing `session-cleanup` SessionEnd hook
- Trigger event: `PostToolUse(Edit|Write)` — counts real change events, avoids latency on the hot `PreToolUse` path
- Suppression rules: skip suggestion when `.claude/state/session.json` `role == worker` AND Plans.md has any `cc:WIP` row (mirrors PreCompact role-gate); skip when an active `[ralph]` task is mid-loop
- Script home: `harness/skills/harness-compact/scripts/suggest-compact.sh` (skill-local, invoked from `hooks.json` via `${CLAUDE_PLUGIN_ROOT}/skills/harness-compact/scripts/...`) — keeps suggester cohesive with the skill that owns it

## Phase 90: Plugin name reference cleanup — unify all subagent prefixes to `harness:` (plugin name SSOT)

Created: 2026-05-03

**Goal**: The canonical plugin name declared in `.claude-plugin/marketplace.json` is `harness`. Per Claude Code's `<plugin-name>:<agent-name>` resolution semantics, every subagent reference should use `harness:<agent>` — e.g. `harness:worker`, `harness:reviewer`, `harness:ralph-worker`. Today the repo has **46 wrong-prefix references across 21 markdown/template files**: most are `claude-code-harness:` leftovers from before the v3 rename, plus 6 spillover references introduced in Phase 89 that incorrectly used `powerball-harness:` (which is the repo name, not the plugin name). ## Phase 89: Bring Ralph Loop into Harness — `[ralph]` tasks in `harness-plan` + new `harness-ralph-loop` skill driving subagent iteration

Created: 2026-05-03

**Goal**: Add a Ralph-Wiggum-style iterative-loop execution mode to harness. `harness-plan` learns to detect Ralph-suitable tasks (well-defined success criteria, "iterate-until-pass" patterns) and emits them with a new `[ralph]` marker plus per-task `Verify:` and `MaxIter:` lines. A new `harness-ralph-loop` skill orchestrates the loop: it owns one persistent worktree, dispatches a fresh `harness:ralph-worker` subagent per iteration, runs the verify command authoritatively (anti-tamper hard stop on worker self-report mismatch), scans for both a `<promise>{DoD}</promise>` text tag and a structured `ralph-worker-report.v1` field, diffs the worktree to detect stuck iterations, and stops on success / `FT-RALPH-01` / `FT-RALPH-02` / `FT-RALPH-03`. `harness-work` delegates `[ralph]` tasks to the new skill.

**Motivation**: Many harness tasks already match Ralph's sweet spot (greenfield "build until tests green", fix loops, refactors with regression coverage), but harness has no mechanism to express "iterate until X exits 0". The upstream `/ralph-loop` plugin can't be reused as-is because its Stop hook is session-bound and won't fire inside a Task subagent — and the user wants Ralph work to run in subagents (isolation, parallelism with non-Ralph tasks). So harness builds its own orchestrator that mirrors Ralph's "same prompt, see your work via files" philosophy without depending on the Stop-hook plumbing.

**Source**: User request (this session) + opus-agent architectural review at `/Users/hbai/.claude/plans/help-me-investigate-serialized-curry.md` (full design + decisions table). Opus review corrected three premises: (1) `isolation="worktree"` is fresh-per-call so the orchestrator must drive worktree reuse via `EnterWorktree(path=...)`; (2) the existing `claude-code-harness:worker` agent cannot be reused (hard-coded `isolation: worktree` in frontmatter, TDD-shaped initialPrompt, SR-5 conflicts with Ralph's scratchpad-file pattern) — a sibling `ralph-worker` agent is required; (3) verifier-mismatch (worker self-reports verify pass when actual verify fails) is a load-bearing hard stop, not just a warning.

**Non-goals**: parallel execution of multiple `[ralph]` tasks (deferred — each main session can drive one Ralph orchestrator at a time, sequential by default); upstreaming the orchestrator pattern back to `/ralph-loop` plugin; cross-session resume after `/clear` mid-loop (worktree path is durable but loop state isn't checkpointed yet).

## Phase 83: Native Go PII Guard (port claude-privacy-guard into the Go engine)

Created: 2026-04-28

**Goal**: Replace the Node.js scripts in [claude-privacy-guard](https://github.com/datumbrain/claude-privacy-guard/tree/main/scripts) with a native Go implementation under `go/internal/piiguard/`, exposed as new `bin/harness hook pii-*` subcommands. Wire it into `harness/hooks/hooks.json` so PII / secret detection runs on the user prompt (UserPromptSubmit), tool inputs (PreToolUse: Bash | Read | Write | Edit), and tool outputs (PostToolUse: Bash | Read). On a finding, block via Claude Code's hook decision API — no opt-in scanning, no in-place redaction. Timeout per hook: 2 seconds.

**Motivation**: claude-privacy-guard ships a Node.js UserPromptSubmit hook that blocks prompts containing 90+ secret/PII regex matches. It only covers user prompts, requires Node.js at runtime, and adds another binary to the dependency surface. Harness already runs a Go-native hook engine — folding this capability into `bin/harness` removes the runtime dependency, broadens coverage from "user prompts only" to "every tool I/O", and gives us one place to maintain the regex catalog. This closes the symmetric gap with the existing `go/internal/guardrail/` engine: guardrail covers tool *operations* (R01–R13: file paths, shell commands, tampering); piiguard covers tool *content* (secrets, PII).

**Source upstream**: Reference implementation at `github.com/datumbrain/claude-privacy-guard` MIT-licensed. Specifically: `scripts/prompt-guard.js` (decision flow), `src/scanner/engine.ts` (PrivacyScanner class), `src/scanner/detectors.ts` (BUILTIN_RULES + `loadExternalRulesFromJson`), `data/regex_list_1.json` (90-pattern external catalog). All to be re-implemented in Go, not vendored as JS.

**Design**:
- `go/internal/piiguard/` — new package: `Rule` struct (id, title, severity ∈ {critical,high,medium,low}, category ∈ {secret,pii}, pattern *regexp.Regexp), `Scanner` (slice of compiled Rules + `Scan(text) ScanResult`), `ScanResult` (Findings, RiskScore, Summary by category).
- `go/internal/piiguard/builtin.go` — port BUILTIN_RULES: email, JWT/Bearer, GitHub/HF tokens, AWS / OpenAI / Anthropic / Google / Groq / Perplexity / Stripe keys, SSH/RSA/EC private keys.
- `go/internal/piiguard/external.go` + `data/pii-regex.json` — port the 90-pattern external catalog; loaded with `codingOnly: true` filter (matches upstream default).
- `go/internal/piiguard/scanner.go` — `Scan(text)` returns findings, weighted risk score (critical=100, high=50, medium=20, low=10, capped at 100).
- New cmd handlers in `go/cmd/harness/hook_pii_*.go`: `hook pii-prompt` (UserPromptSubmit), `hook pii-pretool` (PreToolUse), `hook pii-posttool` (PostToolUse). Reuse one shared `runPIIGuard(input, blockMode)` helper; the three commands differ only in how they read the input and how they format the block decision.
- **Block protocol per event** (matches CC hook decision API):
  - UserPromptSubmit → `{"decision": "block", "reason": "🛡️ Privacy Guard blocked …"}` + exit 1 (mirrors claude-privacy-guard exactly)
  - PreToolUse → `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "…"}}` + exit 0 (CC v2.1.77+ deny semantics)
  - PostToolUse → `{"decision": "block", "reason": "…", "additionalContext": "<redacted output>"}` + exit 0 (CC PostToolUse cannot undo, but `decision:block` feeds reasoning back to Claude with a redacted view of the leaked data)
- **Hook config**: append three new entries to `harness/hooks/hooks.json` — UserPromptSubmit (matcher `*`), PreToolUse (matcher `Write|Edit|MultiEdit|Bash|Read`), PostToolUse (matcher `Bash|Read`). All `timeout: 2`.

**Non-goals**:
- Hooking PreToolUse `Task` / MCP tool calls (out of scope, separate phase if desired).
- Custom user allowlist UX — `.privacy-guard.json` config file is a follow-up; v1 ships with a hard-coded `disabledRules` env var (`HARNESS_PIIGUARD_DISABLED_RULES`).
- Vendoring or transpiling the upstream JS (Go re-implementation only).
- Replacing the existing 13-rule guardrail engine (piiguard runs alongside it).
- Removing the existing claude-privacy-guard plugin from a user's setup (docs will note the overlap; users can keep both, but Harness's piiguard is the recommended path inside this plugin).

**Risk notes**:
