## Phase 86: PII Guard email allowlist for GitHub noreply addresses + rebrand block message to Powerball Harness PII Guard

Created: 2026-05-01

> **Editing convention for this phase**: The PII Guard hooks scan this file and the unfixed `email-address` rule will block any literal email-shape. Whenever this phase needs to refer to an email, ALWAYS wrap the local part in angle brackets — e.g. `<USER>@users.noreply.github.com` or `<ID>+<USER>@users.noreply.github.com`. The angle brackets break the word boundary the regex requires, so the engine never sees a match. Bare email-shape literals (with a real local-part before the `@`) are forbidden until task 86.1 ships. The Phase 85 reserved names continue to apply only when expanded verbatim.

**Goal**: Two small, related polish items reducing PII Guard noise and clarifying ownership of the warning text:
1. **Email allowlist for GitHub noreply addresses**: stop flagging emails whose domain part is `users.noreply.github.com`. These are GitHub's privacy-preserving commit/PR addresses — designed to be public, never personal contact info — so blocking them is pure noise. Both forms must pass: the legacy `<USER>@users.noreply.github.com` and the modern numeric-prefix `<ID>+<USER>@users.noreply.github.com`. A whole-domain match (after the last `@`) covers both.
2. **Rebrand block/warn messages to "Powerball Harness PII Guard"**: the current text says generic "Privacy Guard" / "🛡️ Privacy Guard blocked this submission". Users seeing the warning don't know which system flagged it or that it's a Powerball-specific guardrail (vs. a generic Claude Code feature). Replace all five user-facing strings in `go/cmd/harness/hook_pii.go` with "Powerball Harness PII Guard".

**Motivation**: User reported (a) GitHub noreply commit emails are flagged as PII even though they're explicitly designed for public exposure — the whole point of the noreply domain is to be safe to publish — and (b) the block message reads as a generic "security guard" with no Powerball Harness branding, so users can't tell what system flagged them or where to look for documentation. Both are 30-minute fixes that compose cleanly with the Phase 85 `Validator` field already on the `Rule` struct.

**Source**: New work, requested by user. Builds on the per-rule `Validator` field added in Phase 85 task 85.1 (`go/internal/piiguard/rule.go:44`) and the `formatPromptBlockReason` / `formatPostToolContext` text introduced in Phase 83.

**Risk notes**:
- **Allowlist-by-domain over-trust**: a phisher could spoof a `From:` header claiming the noreply domain in pasted email content. Mitigation: the allowlist only suppresses the *PII tag* on the email itself, not any of the surrounding content. If the surrounding content contains a real secret (token, key, etc.), the other rules still fire. Email-only false-negatives are acceptable for a domain that is by design public.
- **Substring confusion**: a naive suffix match would also pass a decoy like `evil-users.noreply.github.com.attacker.example` — the validator uses `strings.EqualFold` on the full domain (everything after the last `@`), not `strings.HasSuffix`, to prevent this. Test case (d) in task 86.1 asserts this explicitly.
- **Rebrand string-coupling**: any external doc, README, or screenshot asserting on the old "Privacy Guard" wording will drift. Mitigation: search the repo for "Privacy Guard" before merging — `grep -rn 'Privacy Guard' .` — and either update or note the drift in the CHANGELOG. Most matches will be in `piiguard` upstream-provenance comments which intentionally stay.
- **Fixture-write self-block**: same bootstrap problem as Phase 85 task 85.4 — writing the negative fixture via Edit/Write triggers the unfixed PII Guard hook. The task DoD pre-emptively mentions the workaround. Building task 86.1 first solves it cleanly because the validator then exempts the fixture content.
- **Future allowlist growth**: if more domains accumulate, the hardcoded slice becomes a churn point. Mitigation: explicitly out-of-scope this phase; revisit as an env-var or settings-file-driven list once the slice exceeds three entries.
- **Editing-convention compliance for this phase block**: any future edit to this Phase 86 block that introduces a literal email shape (without angle-bracket placeholders) will fail the pre-tool-use PII Guard hook until 86.1 ships. After this phase ships, the editing convention can be relaxed in a follow-up edit because noreply-domain literals will pass cleanly.
